# **ゴッドフィールド AI環境 (C++) 実装仕様書**

本ドキュメントは、強化学習（PPO等）を用いてゴッドフィールドのAIを学習させるための、C++ベースの超高速・高並列シミュレータ（Vectorized Environment）の実装仕様を定義する。

## **1. 全体アーキテクチャ方針**

* **データと処理の分離**: ゲームの状態（Trivially Copyableな構造体）とゲームロジック（関数群）を完全に分離する。
* **視点の正規化 (Canonicalization)**: AI（Python側）には常に「行動権を持つプレイヤー（Current Actor）」の視点に変換（マスキング等）した観測データを渡す。
* **デュアル・バッファ設計**: C++のみが知る「真の内部状態」と、AIに渡すための「観測バッファ」を別々に管理し、完全なゼロコピー連携と情報隠蔽（カンニング防止）を両立する。

## **2. 定数・ハイパーパラメータ定義**

コードの保守性を高めるため、定数はマクロまたは constexpr として外部定義・一元管理する。

具体的な定義は [constants.h](../godfield_core/src/constants.h) [types.h](../godfield_core/src/types.h) を参照。

## **3. データ構造 (Data Structures)**

すべての構造体は `std::memcpy` 可能なプリミティブ型で構成し、キャッシュライン（64バイト）を意識したメモリアライメント (`alignas(64)` または `alignas(32)`) を適用する。

- **カード共通特徴量フォーマット (CardFeatures)**:\
  疎なベクトル（Sparse Vector）として、全カードのパラメータを固定長で表現する。マスターデータ読み込み時に構築し、C++のメモリ上に保持する。


- **イベント構造体 (GameEvent)**:\
  履歴に残す過去の行動記録。1つのイベントを固定サイズで表現する。

- **観測バッファ (Observation)**\
  Python（AI）にゼロコピーで渡すための構造体。内部状態から「翻訳」されて生成される。

- **内部状態 (InternalState)**\
  C++だけが知る真のゲーム状態。

具体的な定義は [types.h](../godfield_core/src/types.h) を参照。

## **4. 行動空間とマイクロステップ**

### **4.1 21次元のアクション定義 (Action Space)**

AIは常に長さ121のロジット（確率）を出力する。マスクにより強制的に選択肢が絞られ、ターゲット（自分か相手か）もここで決定する。

* 0 ～ 17: 手札のインデックスを選択（カードを仮置き場へ）
* 18: **確定（相手をターゲット） / 買う(YES) / （防具ゼロのままなら）そのまま受ける**
* 19: **確定（自分をターゲット） / 買わない(NO)**
* 20: **祈る（ドロー）**
* 21~121: **両替における数値選択 (0~99)**

※メインフェイズ等において、自分にも相手にも使えるカード（武器や奇跡、回復など）を仮置きした場合、C++のアクションマスクは 18 と 19 の両方を 1.0 にして、AIに高度なターゲット選択（自分撃ち等）を委ねる。

※防御フェイズにおいて、防具を置かないまま 18 を押すことが「そのままダメージ等を受ける」行動として処理される。

### **4.2 マイクロステップの処理フロー (step関数)**

1. C++は行動を受け取り、`current_actor_id` の行動として `InternalState` を更新する。
2. アクションが「仮置き（0~17）」の場合、状態を更新し、重ね掛け可能なカードのマスクのみを 1 にした新しい `Observation` を生成。
3. アクションが「確定（18 または 19）」あるいは「祈る（20）」の場合、C++は乱数を振り、指定されたアクションやターゲットに基づいてダメージや効果を解決する。
4. 行動権が相手に移る場合、`current_actor_id` を反転させ、相手視点で `Observation` を生成する。
   * **マスキング処理:** 相手の `true_hand` から公開されているカード（`is_known_to_opp` または `is_deployed` が true）のみを抽出し、スロット位置のリークを防ぐために `opponent_hand_cards` 配列の左詰めで配置し、残りのスロットは 0 でマスクする。
   * **イベント履歴の反転:** `GameEvent::actor` を現在の行動プレイヤーから見て 0(自分) か 1(相手) になるよう、XOR演算で高速に反転させて渡す。
   * **終末の時の判定:** `current_turn >= APOCALYPSE_TURN` であれば、`is_apocalypse` フラグを立てる。

> [!NOTE]
> **部分観測（POMDP）下における公開手札（is_known_to_opp）の解釈と重複排除仕様**
> `is_known_to_opp` フラグは本家ゴッドフィールドには存在せず、強化学習エージェントが「相手の手札について確定で知っている主観情報」をモデル化するために追加されたプロパティです。スロット位置情報が非公開（AIには左詰めされて渡される）である特性上、以下の重複排除ロジックを適用しています。
> 
> * **「買う」を拒否（買わなかった）した場合の挙動:**
>   提示されたカードを買わなかった場合、そのカードは相手の手札に戻って伏せられます。この際、もし相手の手札内に既に同じカードタイプで公開状態（`is_known_to_opp == true`）のカードが存在していた場合、新たに提示されたカードの公開フラグは `false`（非公開）に戻します。
>   なぜなら、スロット位置が見えない観測者からすると、「すでに知っている手札内のカードを見せられた」のか「新規のカードを見せられた」のかを識別できないため、主観的な確定情報としては「少なくとも1枚は手札に持っている」という事実のみに留まるからです。二重に `true` にしてしまうと、AIは「相手が公開状態のカードを2枚持っている」と過大評価するリークが発生してしまいます。
> * **例外（奇跡カードとの関係）:**
>   フィールド上にすでに「展開済み（`is_deployed == true`）」の同名奇跡が存在する場合であっても、手札内（未展開）の奇跡が新たに提示された場合は、手札の公開フラグは `true` のまま維持します。展開済みの奇跡と手札内の未展開の奇跡は、手札追加攻撃や将来的な取引対象になるなど、ゲーム上全く異なる価値を持つ別情報であるためです。

## **5. 報酬設計と終端状態キャッシュ**

ゴッドフィールドの強化学習では、勝敗確定時のスパースな終端報酬（勝利: +1.0, 敗北: -1.0, 引き分け: 0.0）を基本として学習を行います。

### **5.1 終端観測の消失防止 (Terminal Observation Cache)**

On-Policyな学習アルゴリズム（PPOなど）において、価値関数の正確なブートストラップを行うためには、エピソード終了時（`is_done == true`）の最後の観測状態（SB3 では `info["terminal_observation"]`）が不可欠です。しかし、EnvPoolは完了した環境をそのステップ内で自動リセットするため、何も対策をしないと「リセット後の初期状態」のみが返され、真の終端観測が消失してしまいます。

この問題を解決するため、C++の `EnvPool` 内に以下のキャッシュ機構を実装しています：

1. **キャッシュバッファの追加:** `EnvPool` に終端観測保存用バッファ `terminal_obs_buffers_[2]` を追加。**プレイヤーごとに1本ずつ**持つ点が重要です（理由は下記）。
2. **リセット直前のキャッシュ生成:** `step_env` 内で `is_done` と判定された際、`reset_env` を呼び出して環境状態を初期化する**直前**に `make_observation` を実行し、終端時点の観測を両プレイヤー視点で保存。
3. **Python側への連携:** Pythonバインディングに `get_terminal_observations_for(player_id)` を公開し、`env_wrapper.py` の `step_wait` 内で `info["terminal_observation"]` にキャッシュされた終端状態を設定して SB3 に渡す。

**なぜプレイヤーごとに持つのか:** 決着は学習者の手番だけでなく、相手の手番でも起こります。行動者視点の終端観測をそのまま使うと、相手の攻撃で負けた場合に「相手視点の盤面」でブートストラップしてしまいます。同じ理由で報酬も `get_rewards_for(player_id)` で学習者視点のものを取得します（行動者視点の `get_rewards()` は相手が勝ったときに符号が逆になります）。

### **5.2 ターン数による打ち切りは行わない**

上級者同士の対戦では稀に膠着状態が生まれ、150ターンの「終末の時」に突入して決着します。エージェントにこの展開まで学習させたいため、**ターン数による人為的なエピソード打ち切りは行いません**。決着はゲームルール（`run_death_check`）のみが決定します。

打ち切りを安全弁として使えないため、**進行不能な状態を作らないこと自体が要件**になります。合法手が0件になる状態は `tests/test_rl_pipeline.py` が検知します。

なお `TURN_PROGRESS_SCALE_TURNS`（300）は観測 `turn_progress` の正規化基準であり、ゲームの打ち切りには使いません。`current_turn` はこの値を超えうるため、`turn_progress` 側で 1.0 に飽和させています。

## **6. 環境プール (EnvPool) の並列設計**

10,000ゲーム規模の極限効率化を実現するため、C++ の `EnvPool` およびスレッドセーフ設計を導入しています。

### **6.1 OpenMP による高並列化**
* `step_all` におけるバッチ処理のループに対して OpenMP プリジデント `#pragma omp parallel for` を適用し、複数スレッドで各環境のシミュレーションを並列実行します。
* メモリは事前に `std::vector<InternalState>` および `std::vector<Observation>` として一括確保されており、False Sharing（偽共有）を防ぐために `alignas(64)` を適用しています。

### **6.2 スレッドセーフな乱数・カード抽選**
* 各環境の乱数生成器（`rng`）は環境個別の `InternalState::rng` に格納されており、完全にスレッドローカルで動作します。
* 一方、山札からのカード出現確率を司る `g_drop_distribution`（`std::discrete_distribution`）はグローバルに共有され、そのサンプルメソッド `operator()` は非constで内部状態を書き換えるため、スレッド間でデータ競合（Data Race）を起こすリスクがあります。
* これを防ぐため、`card_registry.cpp` の `draw_card` 内に `std::mutex`（`g_distribution_mutex`）を用いた排他制御を導入し、マルチスレッド環境下における安全な同時抽選を保証しています。

### **6.3 シードの衝突回避**
* 各並列環境の初期シードは `seed_ + env_id` でユニークに設定されます。
* 自動リセット時のシードには `seed_ + num_envs_ * (1 + reset_counts_[env_id]++) + env_id` を用いることで、リセット回数や環境IDが異なるすべてのシミュレーション実行において同一のシード（同一ゲーム展開）が衝突しないように設計されています。

## **7. Python / Pybind11 API インターフェース**

C++で実装した `EnvPool` をPythonモジュールとして公開し、OpenAI Gym (Gymnasium) に似たAPIを提供する。

```cpp
#include <pybind11/pybind11.h>
#include <pybind11/numpy.h>

class EnvPool {
public:
    // ゲームの初期化
    // 運の要素を完全に同一にして複数エージェントを評価・比較する
    // Duplicate Evaluation に備え、シードの固定機能は必須とする。
    void reset(int seed);
    
    // AIの推論結果の配列を受け取り、シミュレーションを進行する
    // actions は [バッチサイズ] のnumpy配列 (int32)
    void step_all(pybind11::array_t<int> actions);
    
    // 相手の手番の環境だけを進める（単一エージェント化のため。8.2節参照）
    void step_subset(pybind11::array_t<int> env_ids, pybind11::array_t<int> actions);

    // 推論待ちになったゲームの Observation バッファのポインタを返す
    // [バッチサイズ, 観測次元数] の float32 配列としてPython側にゼロコピーで覗かせる
    pybind11::array_t<float> get_observations();

    // 各環境で現在行動権を持つプレイヤーID（InternalState をコピーせず手番を知るため）
    pybind11::array_t<int> get_current_actors();

    // 終局時の報酬・観測を指定プレイヤー視点で返す（5.1節参照）
    pybind11::array_t<float> get_rewards_for(int player_id);
    pybind11::array_t<float> get_terminal_observations_for(int player_id);
};
```

## **8. 強化学習エージェントの学習方針**

### **8.1 アルゴリズムの選定: PPO (Proximal Policy Optimization)**

行動空間が完全に離散化された21次元の環境に対し、学習の安定性とハイパーパラメータの堅牢性に優れる PPO を採用する。

C++側の10,000並列環境から生成される膨大な経験データを、方策勾配法によって高速に学習させる。

### **8.2 自己対戦 (Self-Play) と単一エージェント化**

視点の正規化（常に手番プレイヤー視点に変換する）により、エージェントは1つのニューラルネットワークモデルを共有しながら自分自身と対戦する。これにより、特定の戦術に過学習することなく、ナッシュ均衡に近づくプレイングを自律的に獲得する。

ただし**学習データの並べ方には注意が必要**である。

#### **なぜ手番をそのまま流してはいけないか**

PPO は単一エージェントMDPを前提としており、ロールアウトバッファ上で連続する遷移は同じエージェントのものだと仮定してGAEを計算する。

```
V(s_t) ← r_t + γ · V(s_{t+1})
```

2人ゲームの手番をそのまま流すと `s_{t+1}` は**相手視点の観測**になる。ゼロサムゲームでは `V(相手視点) ≈ -V(自分視点)` なので、符号を反転させないと「自分の手の後に相手が有利になった」ことを「自分の行動が良かった」と学習してしまう。

さらにこのゲームでは手番が厳密に交互ではない（仮置き→仮置き→確定のように同じプレイヤーが複数ステップ連続で意思決定する）ため、「毎ステップ符号反転」という単純な対処も誤りになる。

#### **採用している構成: 相手の手番を環境の内部で消化する**

`GodFieldVectorEnv` は `learner_seat`（学習者の座席）と `opponent`（相手方策）を受け取り、相手の手番を `_advance_opponent_turns()` が環境内部で処理する。SB3 には**学習者の意思決定点だけ**が見える。

- バッファ上の連続する遷移が同じエージェントのものになり、符号の問題が構造的に発生しない
- 報酬の帰属が明確になる（`get_rewards_for(learner_seat)` を使う）
- 正しさの不変条件が「バッファに学習者の遷移しか入らない」という単純な形になり、テストで検証できる

**相手の強さは落ちない。** 自己対戦は「凍結した自分のコピーを `opponent` に渡す」ことで実現する。同一のネットワーク・同一のアルゴリズムであり、数十イテレーションごとにスナップショットを更新する。凍結する理由は2つある。

1. 生きた方策の遷移もバッファに入れると交互構造に戻り、符号の問題が再発する
2. 勾配更新のたびに相手が変わると動く標的を追うことになり、学習が不安定になる

#### **相手方策の段階的な移行**

`godfield_rl/opponents.py` の `Opponent` プロトコルに準拠すれば差し替えられる。

| 段階 | 相手 | 目的 |
|---|---|---|
| 1 | `RandomOpponent` | 学習の下限を測る |
| 2 | `HeuristicOpponent` | パイプラインの正しさを確定させ、解釈可能な指標を得る |
| 3 | 凍結した自分のコピー | 真の自己対戦 |

段階2を経由する理由は、**自己対戦だけでは勝率が常に50%付近に張り付き、強くなっているか分からない**ことにある。ヒューリスティックへの勝率は最終段階でも評価指標として残す価値がある（ランダム方策の勝率は約32%であり、有意な差が出る）。

#### **データ効率について**

この構成では相手側の遷移を学習に使わないため、シミュレートしたゲーム1ステップあたりのサンプル数は半分になる。ただしC++シミュレーションは十分に安く、実質的な追加コストは「勾配なしの推論1回分」である。

また、ランダム要素の強いこのゲームでは配牌の運が分散の主要因になる。これに対しては両視点を使うより、**同一シードで座席を入れ替えたペアを走らせる（duplicate play）**ほうが直接的で、正しさも自明である。`reset_env(env_id, seed)` が環境ごとにシードを取るため実装の足場はある。

### **8.3 スパース報酬問題と補助タスク**

勝敗確定まで報酬がゼロである期間（スパース報酬）における学習速度を担保するため、AIのネットワーク（Critic等）に以下の補助予測タスク（Auxiliary Tasks）を課す。

* **次ターンのHP/MP予測:** 「この行動を取った後、自分と相手のステータスはどう変動するか」を予測させる。
* **相手の手札推論 (Belief State):** 「0埋め」された相手の手札スロットの中身について、イベント履歴から真のカードを予測させる。

## **9. C++環境実装で求められる絶対要件 (コーディングの鉄則)**

これからのC++実装フェーズにおいて、バグの温床を根絶し極限効率を達成するために、以下の要件を**絶対遵守**する。

1. **Trivially Copyable なデータ構造の徹底**
   * 盤面状態やイベント履歴の構造体には、`std::string`、仮想関数 (`virtual`)、動的コンテナ (`std::vector` など)、ポインタを**一切含めない**こと。
   * 全て固定長の配列とプリミティブ型で構成し、`std::memcpy` で一瞬でコピー・移動できるようにする。
2. **厳密なルール・ステートマシン（アクションマスクの絶対的正確性）**
   * 「アクションマスクの生成」がAIの命綱となる。「今は攻撃フェーズの1枚目」「今は防御フェーズで、相手は火属性武器の攻撃をしてきている」といったゲームの進行状態（State）を厳密に管理する。
   * **絶対にルール違反の行動が 1.0（選択可能）にならないようにする。** マスクに抜け穴があると、AIは瞬時にそれを見つけ出してゲームを破壊する。
3. **算数と確率のオフロード（AIに計算させない）**
   * **AIは数学者ではなくゲーマーである。** 飛んできているダメージ量の計算や、防具の合計値の計算など、C++で確定できる算数は全てC++側で行い、結果を Observation に乗せて渡す。
   * 確率的なカードの効果（命中率など）は、AIが「確定」した直後にC++側でサイコロ（乱数）を振り、その結果を「事後報告」としてイベント履歴に書き込む。AIに未来の確率を予測させつつも、乱数シードそのものは隠蔽する。
