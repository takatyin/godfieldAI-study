# 強化学習の構成

学習まわりの「いま何がどうなっているか」と「なぜその形なのか」をまとめます。
ゲームのルールそのものは `rules.md` / `phase_specifications.md` を、
C++ コアの構造は `core_architecture.md` を参照してください。

数値は実装から確認したものです。定数は C++ の `constants.h` と
`godfield_rl/config.py` が唯一の情報源で、この文書はその写しにすぎません。
食い違いを見つけたらコードのほうが正です。

---

## 1. 全体像

| | |
| --- | --- |
| アルゴリズム | SB3-Contrib `MaskablePPO`（行動マスク付きPPO） |
| 環境 | C++ の `EnvPool`。既定 1000 並列、OpenMP でステップを並列化 |
| 観測 | 942 次元（うち合法手マスク 122） |
| 行動 | 122 次元の離散 |
| 特徴抽出 | Transformer（既定 d_model=192 / 8ヘッド / 4層） |
| 学習形態 | 4GPU の非同期リーグ（自己対戦 ＋ 手書き方策） |

エントリポイントは `train.py`、リーグ一式の起動は `scripts/run_league.sh` です。

## 2. 観測 (Observation)

`godfield_core/src/types.h` の `Observation` 構造体がそのまま
float の1次元配列になります。オフセットは `godfield_rl/feature_config.py`
が持ち、C++ 側と一致していることを `tests/rl/test_observation_layout.py`
が検証します。

| 区間 | 次元 | 内容 |
| --- | --- | --- |
| 0–5 | 6 | HP / MP / 所持金（自分・相手） |
| 6–15 | 10 | 病（なし・風邪・熱病・地獄病・天国病） |
| 16–23 | 8 | 呪い（霧・閃光・暗雲・夢） |
| 24–45 | 22 | 守護神 |
| 46–50 | 5 | 飛んできているダメージ、仮置き防御の合計、終末フラグ、ターン進行 |
| 51–52 | 2 | 手札枚数（自分・相手） |
| 53–70 | 18 | フェイズの one-hot |
| 71–142 | 72 | カードID（自分の手札・仮置き・相手の手札・相手の仮置き） |
| 143–178 | 36 | カードごとのフラグ（自分の公開状態・相手の展開状態） |
| 179–818 | 640 | イベント履歴 128 件 × 5 |
| 819 | 1 | 履歴の書き込み位置 |
| 820–941 | 122 | 合法手マスク |

### 設計上の要点

**計算はC++側で終わらせる。** 飛んできている総ダメージや仮置き防御の合計は
確定した算数なので、方策に足し算を学ばせず結果だけを渡します。

**部分観測は明示的に潰す。** 霧がかかると相手の HP/MP/所持金・病・呪い・守護神は
0 埋めされます。ただし手札の**枚数**は隠しません（場から数えられるため）。

**カード優位が見えるようにしてある。** 手札枚数と公開状態は後から追加した
ものです。これらが無かった頃は「無料で相手の手札を1枚奪える」「防具を捨てると
手札が減る」といった判断がすべて 50% 前後のコイントスになっていました。

## 3. 行動 (Action)

添字は**フェイズによって意味が変わります**。同じ 19 が「自分を対象」でもあり
「確定」でもあります。

| 添字 | 意味 |
| --- | --- |
| 0–17 | 手札スロットの選択（仮置き・防御・出品・廃棄の対象） |
| 18 | 相手を対象 / 買う / 受け入れる |
| 19 | 自分を対象 / 買わない / はね返す / 確定 |
| 20 | 祈る（カードを引く） |
| 21 | 捨てる |
| 22–121 | 数値の指定 0–99（両替の配分） |

合法手マスクは C++ が毎ステップ作り、`MaskablePPO` が非合法手の確率を 0 に
潰します。**進行不能な状態を作らないこと自体が要件**で、合法手が0件になる
状態は `tests/rl/test_rl_pipeline.py` が検出します。

## 4. 単一エージェント化

ゴッドフィールドは2人ゲームですが、PPO は単一エージェントMDPを前提にしています。
手番が交互に現れるロールアウトをそのまま渡すと、GAE が `V(s_{t+1})` に
**相手視点の価値**を使ってしまい、ゼロサムでは符号を反転させないと誤った
価値目標になります。

`GodFieldVectorEnv` は相手の手番を環境の内部で消化し、SB3 には学習者の
意思決定点だけを見せます（`_advance_opponent_turns`）。相手方策は
差し替え可能で、自己対戦では凍結した過去の自分を渡します。

## 5. 特徴抽出器

`GodFieldTransformerExtractor` は観測を**トークンの列**として扱います。

```
系列長 = 1（全体トークン）+ 18×4（カード）+ 128（履歴）= 201
```

カードをスロット位置ではなくトークンとして見るので、「武器＋オーラ」のような
組み合わせを位置に依存せず学べます。先頭の全体トークンが列を要約し、その出力
だけを方策へ渡します。

**空スロットは注意の対象から外します**（`src_key_padding_mask`）。外さないと
空きの多い序盤ほど意味のないトークンに注意が吸われます。ただしこの副作用として
**手札の枚数が表現から消える**ため、枚数は独立した次元として全体トークン側に
渡しています。

### カードの属性を与える

観測に入っているのはカードIDだけです。値段も攻撃力も入っていないため、
294枚それぞれが何をするカードなのかを勝敗の報酬だけから再発見することになり、
実測では 37M ステップ学習しても身についていませんでした。

| 測ったもの | ランダムに選んだ場合 | 学習済みモデル | 最良を選んだ場合 |
|---|---:|---:|---:|
| 売るときに選ぶカードの値段 | 6.2 | 6.0 | 16.7 |
| 主行動で選ぶ武器の攻撃力 | 7.1 | 7.1 | 11.7 |

人手の方策は `feature(cid, "price")` を直接読んで指すので、これは賢さの差では
なく知識の差です。`godfield_rl/card_features.py` がカードマスタから固定の属性
テーブル（値段・攻撃力・防御力・MPコスト・命中率・出現率・属性・種別・使用
タイミング・全体攻撃・リアクション・付与状態）を作り、各カードのトークンに
足します。履歴のカードにも同じものを足します。

### 閾値を表しやすくする

人が書く戦略は「値段15円以上なら売る」「所持金10円以上なら買う」のように閾値で
できています。正規化されたスカラーを線形層に通す形だと、閾値は重み・バイアス・
非線形の組み合わせになり学習が遅くなります。実測でも「買う」を選ぶ確率は
所持金 0〜9円で 13.4%、10〜24円で 19.1% とほぼ平坦でした（人手の方策は
0.2% → 98.6%）。

そこで数値には **温度計符号**（`値 >= 閾値` を閾値ごとに1次元）を併記します。
閾値の判断が重み1つで表せます。生の値も残るので連続的な大小比較も失いません。
カードの属性と、全体トークン側の HP・MP・所持金の両方に入れています。

MLP 版（`GodFieldFeatureExtractor`）も残してありますが、既定は Transformer です。
カード属性と閾値符号は Transformer 版にだけ入っています。

## 6. リーグ学習

単一の固定相手だけで学習すると、その相手の弱点だけを突く方策に落ち着きます。
過去の自分を含む複数の相手と戦わせます。

### プールの構成

1. **錨（anchor）** — 学習を通じて固定の相手。既定は手書き方策 `StrategicOpponent`
2. **分身（snapshot）** — 一定ステップごとに共有ディレクトリへ保存された過去の自分たち

`--anchor-ratio`（既定 0.5）が錨と当たる割合を決めます。

以前は両者を1つのリストに入れて一様に選んでいたため、錨と当たるのは
「1体 ÷ (1体 + 分身5体)」で約17%でした。分身は自分と同じ弱点を持つので、
その弱点は一度も罰されません。実測では 37M ステップ学習したモデルが

- 学習相手（手書き方策の旧版・ヒューリスティック）に 71% / 93%
- 一度も戦っていない相手に 45%

と、**学習相手にだけ強い**方策になっており、「買う」を選ぶ確率は gen4 から
gen36 までほとんど動きませんでした。錨の割合を上げるのは、この閉じた自己対戦から
抜け出すための舵です。

### バッチ単位で相手を切り替える

環境ごとに違う相手を割り当てて個別に推論すると、バッチ処理の利点が消えます。
`PoolOpponent` は `act()` が呼ばれるたびにプールから**1体だけ**選び、その1体が
その回の全環境を一括で推論します。長期的にはすべての環境があらゆる世代と
均等に当たります。

### ワーカーを均等に抽選する

プールへの保存はステップ基準なので、**速いワーカーほど多くのモデルを残します**。
一様に抽選すると対戦相手がその1体に偏ります（実測でプール53個中30個が
最速のワーカーのものになり、遅いワーカーは自分よりはるかに強い相手とばかり
当たって勝率15%に沈んだ）。ほぼ全敗では行動の良し悪しが差として出ません。

`sample_across_workers` はワーカーを巡回して選ぶので、モデルの大きさや速度が
違っても対戦相手の構成が変わりません。

## 7. 更新量をワーカー間で揃える

1ロールアウトあたりの勾配更新回数は次で決まります。

```
更新回数 = ceil(rollout ÷ batch_size) × n_epochs
```

`batch_size` は VRAM で頭打ちになるため、**大きいモデルほど更新回数が増えます**。
実測では `approx_kl` が最小構成の 0.025 に対し、大きい構成では 0.35〜0.44 まで
達していました。この状態では重要度比のクリップばかりが効いて学習が進みません。

対策は3つ組み合わせています。

**勾配チェックポイント** — 層ごとの活性を保持せず逆伝播時に再計算します。
逆伝播が約1.24倍になる代わりに VRAM が減り、`batch_size` を上げられます。
なお注意そのものは PyTorch がメモリ効率カーネルで処理しており系列長に対して
線形なので、ここで削れるのは FFN や射影の活性です。

**n_epochs をワーカーごとに変える** — batch だけでは揃えきれないぶんを調整します。

**target_kl（既定 0.03）** — 方策の変化が閾値を超えたら epoch ループを打ち切る
安全網です。KL の暴走は方策が尖った学習後半に起きるため、固定の設定では
読み切れません。

`scripts/run_league.sh` の worker 表が、この3つを使って全ワーカーを
160更新/rollout に揃えています。

## 8. 報酬

終端の勝敗（±1）が基本です。加えてポテンシャルベースのシェーピング
（`godfield_rl/shaping.py`）を任意で足せます。

```
r' = r + γΦ(s') − Φ(s)
```

この形なら最適方策が変わらないことが証明されています（Ng, Harada, Russell 1999）。
既定では HP 差のみに掛けています。

ポテンシャルは**観測ではなく真の状態**から作ります。観測は霧がかかると相手の
HP/MP/所持金が 0 に潰れるため、そこから作ると霧の付与・解除だけで偽の報酬が
出ます。

## 9. 評価と診断

自己対戦では自分の強さも同時に上がるため、**プール相手の勝率は絶対的な強さを
表しません**。学習ループとは独立した物差しが要ります。

| 道具 | 見るもの |
| --- | --- |
| `tools/evaluate.py` | 固定の相手（既定 strategic）に対する勝率。席を入れ替えて平均する |
| `tools/diagnose_policy.py` | どの局面で何を間違えているか。間違いを上書きして「直す価値」を測る |
| `tools/diagnose_discard.py` | 捨てさせるカードが本当に効く局面だったか（真の状態を読む） |
| `tools/track_learning.py` | 世代を並べて、値が収束したのかまだ動いているのかを見る |

**勝率だけを見ていると方策の潰れに気付けません。** 実際、対象選択フェイズで
100%「相手」を選ぶまで潰れていたモデルが、弱い相手には勝率85%を出していました。
そのとき回復系の雑貨を相手に使っていたわけですが、勝率からは分かりません。

評価に使う相手も選ぶ必要があります。`heuristic` は対象選択が常に「相手」で
固定という強い偏りがあり、勝率が9割を超えて飽和します。上振れも下振れも
見えなくなるので、既定は `strategic` です。
