# 強化学習の試行錯誤の記録

設計の**現在形**は [rl_architecture.md](rl_architecture.md) にあります。この文書は
**何を試して、何が起きて、なぜ今の形になったか**を残すためのものです。

同じ失敗を二度やらないために、次の3つを必ず書きます。

1. 何を変えたか（コード）
2. 何が起きたか（実測値）
3. どうやって気付いたか（どの指標が異常を示したか）

とくに 3 が重要です。この課題の失敗はほぼすべて**例外を出さずに静かに進行**し、
学習は普通の速度で回り、損失も勝率も「それらしい」値を出し続けました。

## 第1期: MLP

最初の特徴抽出器は、カードIDを埋め込んで全部つなげるだけのものでした。
[feature_extractor.py](../godfield_rl/feature_extractor.py) の
`GodFieldFeatureExtractor` として今も残っています。

```python
# カードID 200個（手札18x4 + 履歴128）をそれぞれ16次元に埋め込み、
# 連続値と一緒に1本のベクトルへ連結する
x = concat([
    continuous_features,                       # HP/MP/所持金/フェイズ…
    card_embedding(hand_and_staged_ids),       # 72 x 16 = 1152
    history_continuous,
    card_embedding(history_ids),               # 128 x 16 = 2048
    history_head,
])
features = relu(Linear(x))                     # -> 256次元
```

### 問題

**スロットの位置ごとに別々の重みが割り当てられます。** 「スロット3のパンチ」と
「スロット7のパンチ」は入力ベクトルの別の場所に現れるので、同じカードの意味を
18回ぶん学び直すことになります。「武器 + オーラ」のような組み合わせも、
位置の組み合わせの数だけ覚える必要があります。

## 第2期: Transformer 導入（`b79604d`）

カードを**トークンの列**として扱う `GodFieldTransformerExtractor` を入れました。

```python
tokens = [global_token] + card_tokens(72) + history_tokens(128)   # 系列長 201
out = transformer(tokens, src_key_padding_mask=empty_slots)
features = relu(Linear(out[:, 0]))     # 先頭のグローバルトークンだけを読み出す
```

スロット位置ではなくカードそのものを見るので、位置に依存せず組み合わせを学べます。

### ここで踏んだ罠: 空スロットを注意から外すと手札枚数が消える

空スロットを `key_padding_mask` で注意の対象から外しました。外さないと、空きの
多い序盤ほど意味のないトークンに注意が吸われるためです。

ところがその副作用で、**手札が何枚あるかが表現から完全に消えました**。18枚でも
3枚でも「有効なトークンの集合」しか見えません。第4期で観測に独立した次元として
足し直しています（`ffeeaed`）。

## 第3期: リーグ学習（プール `league_v2`）

自己対戦のプールと人手の方策を混ぜて戦わせる仕組みを入れました
（`7edd7b5`, `54ff5f7`）。ここでは**学習アルゴリズムそのものより、リーグの
運用の不具合**が次々に出ました。すべて例外を出さずに進行するものです。

### 3-1. 全ワーカーが同じ手を指していた（`342cba8`）

`--seed` を渡しておらず、4ワーカーとも既定の 42 を使っていました。

> 実測: ワーカー間の**行動一致率 100%**。seed を変えると 11.6%。

4枚のGPUで同じ計算を4回していたことになります。リーグとして機能していません。

### 3-2. プールの抽選が速いワーカーに偏る（`ef061a2`）

プールへの保存はステップ基準なので、速いワーカーほど多くのモデルを残します。
一様に抽選すると相手がそこに偏ります。

> 実測: プール53個中30個が最速ワーカーのもの。遅いワーカーは自分よりはるかに
> 強い相手とばかり当たり、**勝率15%**に沈んだ。

ほぼ全敗では行動の良し悪しが差として出ません。`sample_across_workers` で
ワーカーを巡回して選ぶようにしました。

### 3-3. モデルを大きくするほど弱くなる（`0956dd0`, `a043b33`）

VRAM の都合で大きいモデルほど `batch_size` を下げていました。ところが
1ロールアウトあたりの勾配更新回数は

```
更新回数 = ceil(rollout / batch_size) * n_epochs
```

で決まるため、**batch を下げると更新回数が跳ね上がります**。

| batch | 更新回数 | approx_kl |
|---:|---:|---:|
| 8192 | 160 | 0.025 |
| 2048 | 630 | 0.42 |
| 1024 | 1250 | 0.35（クリップ率 0.47） |

`approx_kl` が 0.4 では方策が信頼領域を大きく外れ、重要度比のクリップばかりが
効いて学習が進みません。結果、**大きいモデルほど弱い**という逆転が起きました。

> 実測（対 strategic・当時の版）: d128 **68.6%** / d192 50〜54% / d256 **31.4%**

対策は2つです。

- `target_kl`（0.03）を超えた時点で epoch ループを打ち切る
- 勾配チェックポイントで VRAM を削り、batch を上げられるようにする
- そのうえで `n_epochs` で調整し、**全ワーカーの更新回数を160回に揃える**

第4期ではこの逆転が消えました（後述）。

### 3-4. その他の静かな不具合

| 症状 | 原因 | 修正 |
|---|---|---|
| 勝率ログが全部「引き分け」 | シェーピング後の報酬で勝敗を判定していた | `471a948` |
| 観測を変えたのに古いプールを読む | 読み込み失敗を握り潰していた | `3ceec5c`, `5f9ba78` |
| 最終モデルが上書きされる | 全ワーカーが同じ既定パスに保存 | `99db460` |

いずれも「気付くのが数十時間後」になる種類のものです。`5f9ba78` では
**学習開始前に**プールが読めるかを確かめるようにしました。

## 第4期: 観測の拡張（プール `league_v3`）

観測に**手札枚数と公開状態**（相手に見えているか / 展開済みか）を足しました
（`ffeeaed`）。第2期の「空スロットを外すと枚数が消える」問題の穴埋めです。

4ワーカー × 50M ステップを完走しました。

### 結果: 全員が同じ場所に着いた

| worker | 構成 | 対 strategic | 対 heuristic | 対 random |
|---:|---|---:|---:|---:|
| 0 | d128 h4 L2 ent.003 | 44.9% | 92.9% | 97.1% |
| 1 | d192 h8 L4 ent.010 | 46.6% | 94.0% | 97.4% |
| 2 | d192 h8 L4 ent.010 | 46.2% | 94.3% | 97.6% |
| 3 | d256 h8 L6 ent.030 | 45.2% | 94.3% | 97.8% |

第3期の逆転（d128:68.6% / d256:31.4%）は消え、**モデルの大きさによる差が
ほぼ無くなりました**。更新回数を揃えた効果です。

一方で天井は動きませんでした。

| gen | worker 0 | worker 1 | worker 2 | worker 3 |
|---:|---:|---:|---:|---:|
| 10 | 34.0% | 42.9% | 39.4% | 34.7% |
| 30 | 43.9% | 44.6% | 45.5% | 44.5% |
| 50 | 46.2% | 48.1% | 47.2% | 45.4% |

**10M までに大半が終わり、残り 40M で得たのは 3〜9pt。** しかも総当たりでは
全ペアが 48〜52%、つまり互いに互角でした。シード・容量・エントロピー係数を
振っても同じ場所に着く以上、個々の設定ではなく枠組みが天井を決めています。

### 診断: カードの意味を学んでいなかった

「選んだカードの属性の平均」を測ると、**ランダムに選んだ場合と区別できません**。

| | ランダム | w0 | w1 | w2 | w3 | 人手の戦略 | 最良を選択 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 売るときの値段 | 6.2 | 6.0 | 6.2 | 6.2 | 6.0 | 16.7 | 16.7 |
| 武器の攻撃力 | 7.0 | 7.2 | 7.1 | 7.0 | 7.0 | 7.0 | 11.5 |

条件付けも学べていません。

| 「買う」を選ぶ確率 | ネット | 人手の戦略 |
|---|---:|---:|
| 所持金 0〜9円 | 13.8% | 0.2% |
| 所持金 10〜24円 | 17.5% | 98.6% |

| 「両替」を選ぶ確率 | ネット | 人手の戦略 |
|---|---:|---:|
| HP 0〜14 | 18.3% | 100.0% |
| HP 35以上 | 20.4% | 0.3% |

両替はむしろ**HPが高いほど確率が上がる**（逆向き）ままでした。

**原因**: 観測に入っているのはカードIDだけで、値段も攻撃力も入っていません。
294枚それぞれが何をするカードなのかを、勝敗の報酬だけから再発見する必要が
ありました。人手の方策は `feature(cid, "price")` を直接読んで指します。
**賢さの差ではなく知識の差**です。

### どこで負けているかの切り分け

人手の方策を土台に、1フェイズだけネットに任せて勝率の落ち方を見ました。

| フェイズ | 人手の方策との差 |
|---|---:|
| **主行動（自分の手番で何をするか）** | **−13.5pt** |
| 防御 | −3.8pt |
| 両替 | −1.3pt |
| 売る / 買う（何を選ぶか） | −0.5 / −0.1pt |
| 対象選択 | **+0.5pt** |
| 追撃（武器プラス） | **+2.3pt** |

弱いのは主行動だけで、追撃と対象選択はネットのほうが上でした。主行動の中身では
「買う」を 5.7%（人手 16.6%）、「売る」を 5.6%（同 13.9%）しか使わず、代わりに
スマイル系・ハート系の雑貨を撃っていました。

ただし**取引の開始判断だけを人手に合わせても勝率は下がりました**（買う+売るで
−2.3pt）。単一の壊れた判断があるのではなく、人手の方策の強さが一貫した組み立て
として効いている、というのが実測から言えることです。

## 第5期: カード属性の追加（プール `league_v4`）— 失敗

第4期の診断を受けて、カードマスタから作った固定の属性表を各カードのトークンに
足しました（`d1d5a47`）。あわせて自己対戦の閉ループを開くため、固定の相手と
当たる割合を約17%から50%へ上げ、弱い相手から強い相手へ移すカリキュラムも
入れました（`a026dcb`）。

**結果は大幅な後退でした。**

| | v3 | v4 |
|---|---:|---:|
| 対 strategic | 44.9% | **21.0%** |
| 対 heuristic | 92.9% | 85.6% |
| 対 random | 97.1% | 93.5% |

しかも成長曲線が**完全に平ら**でした（gen4 21.7% → gen50 22.3%）。
50M ステップ・30時間かけて、ほぼ何も学習していません。

### 原因

トークンの作り方を、こう変えていました。

```python
# v3（正常に学習した）
card_token = card_embedding[id] + type_embedding[slot] + flag_proj(flags)

# v4（学習が止まった）
card_token = card_embedding[id] + type_embedding[slot] + flag_proj(flags) \
           + attr_proj(ATTR[id])          # ATTR は 295x81 の定数表
```

問題は `ATTR` の**全カード平均が 0 でなかった**ことです。

```python
mu = ATTR[1:].mean(axis=0)
norm(mu)                      # = 2.42   <- どのカードにも同じだけ乗る
norm(ATTR[1:] - mu).mean()    # = 2.64   <- カードごとに違う部分
```

`attr_proj(ATTR[id])` は `attr_proj(mu) + attr_proj(ATTR[id] - mu)` に分解でき、
前半は情報を1ビットも持たないのに後半と同じ大きさでした。表の81列のうち25列が
「ほぼ全カードで同じ値」だったためです（`has_drop_rate` は294枚すべて 1.0 など）。

この定数が 200箇所すべてのトークンに一律で足され、最終段の `Linear → ReLU` で
多くの成分が負側に固定されました。

| | v3 | v4 |
|---|---:|---:|
| 常にゼロの出力ユニット | **0 / 256** | **134 / 256** |
| 局面ごとの出力のばらつき | **0.508** | **0.158** |
| `approx_kl` | 0.02〜0.05 | **0.002** |
| 方策のエントロピー | 0.312 | 0.759 |

局面が変わっても特徴量がほとんど変わらない → 方策が状況を区別できない →
勾配が立たない、という連鎖です。

### カリキュラムのせいではないと分かった理由

序盤は heuristic 中心だったのに、**訓練相手の heuristic に対してすら
83.7% → 84.2% で伸びていません**（v3 は 86.5% → 93.5%）。訓練相手にすら勝てる
ようにならない以上、原因はネットワーク側です。

### 修正（`c9b1333`）

**1. 属性表を列ごとに標準化する。**

```python
ATTR_std[1:] = (ATTR[1:] - mu) / std    # 定数成分を引き、尺度を揃える
# norm(ATTR_std[1:].mean(axis=0)) == 0.00   （2.42 -> 0.00）
```

定数列（標準偏差0）はゼロになり、何も足しません。

**2. 追加した経路をゼロから始める。**

```python
self.card_attr_gate = nn.Parameter(torch.zeros(1))   # 学習されるスカラー

card_token = card_embedding[id] + type_embedding[slot] + flag_proj(flags) \
           + self.card_attr_gate * attr_proj(ATTR_std[id])
```

`gate == 0` なので、学習開始時点の出力は**変更前とビット単位で同一**です。
勾配は

```
∂L/∂gate = ∂L/∂y · f(x)      # gate=0 でも f(x)≠0 なので立つ
∂L/∂W    = ∂L/∂y · gate · x  # gate=0 の間は 0
```

なので、**ゲートだけが先に動き出し、0 から離れた時点で射影の重みも学習を
始めます**。実測で `d/d(gate) = 4.60`、`d/d(weight) = 0.00`。役に立てばゲートが
育ち、役に立たなければ 0 のまま残るので、どちらに転んでも既存の性能は落ちません。

**なぜ重みのゼロ初期化ではだめか。** SB3 の `ActorCriticPolicy` は構築後に
特徴抽出器全体へ直交初期化（gain √2）をかけ直します。`__init__` で重みを0に
しても消えます（実測でゼロにしたはずの射影の出力が 9.62 残っていました）。
直交初期化は `nn.Linear` / `nn.Conv2d` だけを対象にするので、素の
`nn.Parameter` は生き残ります。

修正後の初期化時（5シード平均）:

| | v3 | v4（壊れた版） | 修正後 |
|---|---:|---:|---:|
| 死んだユニット | 18.8 | 40.0 | 27.2 |
| ばらつき | 0.294 | 0.213 | 0.264 |
| 追加経路の寄与 | — | 大 | **0.00** |

追加経路の寄与が厳密に 0 なので、初期状態の関数は v3 と同一です。残る差は
`nn.Linear` を2つ増やしたぶん乱数列がずれて他の層が違う重みを引いたためで、
v3 自身も 9〜29 とばらついています。

### 副産物: 参照の共有

`torch.as_tensor` は numpy 配列とメモリを共有します。`lru_cache` が返す表を
そのまま buffer にしていたため、**抽出器が複数あると同じバッファを共有**して
いました。`clone()` するようにしています。

## 実装に落とした教訓

失敗のたびに「気を付ける」ではなく、構造で防ぐようにしています。

| 教訓 | どう実装したか |
|---|---|
| 後から足した特徴が既存の学習を壊す | ゲートを0から始める（[test_added_paths_start_inert.py](../tests/rl/test_added_paths_start_inert.py)） |
| 定数成分は情報を持たないのに表現を潰す | 表を列ごとに標準化し、テストで共通成分ゼロを固定 |
| 古いプールを黙って読む | 学習開始前に読み込みを試す |
| ワーカーが分岐しない | seed をワーカーごとに変え、一致率を実測 |
| batch を変えると更新量が変わる | `target_kl` で打ち切り、`n_epochs` で回数を揃える |
| 相手が強すぎて勝敗が定数になる | 弱い相手から強い相手へ移すカリキュラム |
| 文書が実装からずれる | [test_docs_match_implementation.py](../tests/test_docs_match_implementation.py) |

### 学習の健全性は起動30分後に必ず見る

第5期の失敗は、この1行で30分後に検出できたはずのものでした。

```bash
grep -oE 'approx_kl *\| [0-9.e-]+' logs/league_worker_0.log | tail -5
```

- **0.02〜0.05** … 健全
- **0.002 前後** … 方策が動いていない。止めて原因を調べる

損失も勝率も fps も「それらしい」値を出し続けるので、ここを見ないと気付けません。

## 未解決のこと

- **カード属性が効くかどうかは未検証です。** 第5期はそれを確かめる実験でしたが、
  実装が学習を壊したので仮説の検証になっていません。判定は「売るときに選ぶ
  カードの平均価格」が 6.2（ランダム）から 16.7（最良）へどれだけ近づくかで
  一発で付きます。
- **カリキュラム（`--anchor-ratio 0.5`）が同時に悪さをしていた可能性**も
  消せていません。ネットワークの欠陥は確定しましたが、両方が効いていた場合は
  修正後も `approx_kl` が低いままになります。
- **本命は探索です。** 主行動の弱さは「今の1手が数手先にどう効くか」の問題で、
  [ISMCTS](../godfield_core/src/ismcts.h) が埋める種類のものです。ただし
  学習済みネットを評価器として繋ぐには、葉をまとめて GPU に投入する実装が
  要ります（葉ごとに Python へコールバックすると GIL 往復で速度が崩壊する）。
